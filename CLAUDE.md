## Project Overview

A ticket/seat booking system with a Fastify + TypeScript backend and a minimal React frontend (not yet implemented). The backend handles trips, seat locking, bookings, and Razorpay payments.

## Backend Commands

All commands run from `./backend/`:

```bash
npm run dev          # Start dev server with hot reload (tsx watch)
npm run build        # Build with tsup (ESM output)
npm test             # Run all tests with Vitest

# Database
npm run db:generate  # Generate migration files from schema changes
npm run db:migrate   # Apply migrations to main DB
npm run db:migrate:test  # Apply migrations to test DB
npm run db:push      # Push schema directly to main DB (no migration file)
npm run db:studio    # Open Drizzle Studio for main DB
```

## Frontend Commands

All commands run from `./frontend/`:

```bash
npm run dev     # Start Vite dev server
npm run build   # Type-check + Vite build
npm run lint    # ESLint
```

## Running with Docker

From the project root:

```bash
docker compose up          # Start all services (API, Postgres, Redis, Ngrok)
docker compose watch       # Start with file sync for development
```

The `docker-compose.yaml` includes separate `postgres` (port 5432) and `postgres_test` (port 5433) containers, plus Redis (6379) and Ngrok (4040) for exposing the API for Razorpay webhooks.

## Running Tests

Tests hit a **real database** — the test DB defined in `.env.test`. The `vitest.setup.ts` loads `.env.test` before any test runs.

```bash
# From backend/
npm test                        # Run all tests
npx vitest run src/modules/bookings/booking.test.ts  # Run a single test file
```

Tests use `beforeAll`/`afterAll` for DB seed/cleanup — they are integration tests, not unit tests with mocks.

## Architecture

### Backend Structure

```
backend/
├── index.ts              # Entry point — calls buildApp() and listens
├── src/
│   ├── app.ts            # Fastify app factory (buildApp)
│   ├── core/
│   │   ├── auth.ts       # JWT plugin (decorates fastify.authenticate)
│   │   ├── guards.ts     # requireRole(...roles) preHandler factory
│   │   ├── emitter.ts    # Typed EventEmitter for internal events
│   │   ├── socket.ts     # Socket.IO plugin with Redis adapter
│   │   ├── errors.ts     # AppError, NotFoundError, ConflictError, etc.
│   │   └── errorHandler.ts  # Global Fastify error handler
│   ├── db/
│   │   ├── index.ts      # Drizzle client (postgres-js driver)
│   │   ├── schema/       # One file per table + relations.ts + index.ts
│   │   ├── queries/      # Reusable Drizzle query helpers
│   │   └── migrations/   # SQL migration files (generated by drizzle-kit)
│   ├── modules/          # Feature modules (auth, trips, seats, bookings, payments)
│   │   └── <module>/
│   │       ├── *.routes.ts      # Fastify route registration
│   │       ├── *.service.ts     # Business logic (static class methods)
│   │       ├── *.validation.ts  # Zod schemas for request/response
│   │       └── *.test.ts        # Integration tests
│   └── types/
│       └── fastify.d.ts  # Augments FastifyInstance (authenticate, io decorators)
```

### Key Patterns

**Route → Service → DB**: Routes use `fastify.withTypeProvider<ZodTypeProvider>()` for end-to-end type safety. Validation schemas are defined in `*.validation.ts` with Zod and passed to the route schema. Services are static-method classes.

**Authentication**: `preHandler: [fastify.authenticate]` on protected routes. JWT payload contains `{ id, role }` and is available as `request.user`. Role enforcement uses `requireRole('admin')` etc. as an additional preHandler.

**Seat locking**: Seats use optimistic concurrency (`version` column). `lockSeat` does a `SELECT ... FOR UPDATE` then updates with `WHERE version = $currentVersion`. Lock duration is 10 minutes. The booking flow requires the seat to already be in `locked` status by the requesting user.

**Payment flow**:
1. Lock seat → Create booking (status: `pending`, seat: `reserved`)
2. Create Razorpay order (`POST /api/v1/payments/:bookingId/order`)
3. Client completes Razorpay checkout
4. Verify payment (`POST /api/v1/payments/verify`) → booking: `completed`, seat: `sold`
5. On failure (`POST /api/v1/payments/failure`) → seat released, booking: `failed`
6. Refunds (`POST /api/v1/payments/refund/:bookingId`) → admin-only, calls Razorpay refund API

**Real-time seat updates**: Services emit `seat:status_changed` via `appEmitter`. The Socket.IO plugin subscribes and broadcasts to `trip:<tripId>` rooms. In test env, Redis adapter is bypassed (in-memory only).

**Error handling**: Throw `AppError` subclasses (`NotFoundError`, `ConflictError`, `UnauthorizedError`, `ForbiddenError`) from services — they are caught by the global error handler and mapped to HTTP status codes.

### Database Schema Relationships

- `trips` → many `seats`, many `bookings`
- `seats` → one `trip`, many `bookings`
- `bookings` → one `trip`, one `seat`, one `passenger`, one `user` (bookedBy)
- `payments` → one `booking` (event log, multiple rows per booking for lifecycle events)

Amounts are stored as **integers (paise)** not decimals.

### API Routes

All routes are prefixed with `/api/v1/`:

| Prefix | Module |
|---|---|
| `/auth` | Register, login, `/me` |
| `/trips` | CRUD trips, seat map, status transitions |
| `/seats` | Lock/unlock seats |
| `/bookings` | Create, list, cancel bookings |
| `/payments` | Razorpay order, verify, failure, refund, webhook |

### Path Aliases

`@/` maps to `backend/src/` (configured in `vitest.config.ts` and `tsconfig.json`).
